# Мониторинг и лимиты LiqScope

## Внешняя проверка (обязательно)

Без внешнего пинга падение сервера видно только по жалобам пользователей.

1. Заведите монитор на `https://liqscope.online/api/health`:
   - **UptimeRobot** (бесплатно, 5 мин): тип HTTP(s), алерт при ключевом
     слове — ответ должен содержать `"status":"ok"`;
   - **Better Stack** (бесплатно, 3 мин): тот же URL, проверка JSON
     `status == ok`, дополнительно можно смотреть `clients < 400`.
2. Алерты — в Telegram-бота проекта: в UptimeRobot integrations есть
   Telegram (бот + chat id), в Better Stack — policy с Telegram-каналом.
   Получатель — chat id админа (`LIQSCOPE_ADMIN_IDS`).

Ручки мониторинга (`/api/health`, `/api/metrics`) никогда не попадают под
rate limit и не кэшируются браузером — пинговать можно хоть раз в минуту.

## Что отдаёт /api/metrics

JSON, скорости — за последнюю минуту:

| Поле | Смысл | Тревога, если |
|---|---|---|
| `ws_clients_total` / `ws_max_clients` | сокеты / кап (400) | > 80% капа — пора думать о 2-м процессе |
| `ws_connects_per_sec` | новых коннектов/с | всплеск в десятки раз — флуд/реконнект-луп |
| `ws_messages_per_sec` | сообщений клиентам/с | 0 при живых клиентах — встал фид |
| `http_requests_per_sec` + `..._by_status` | RPS целиком и по статусам | рост `429` — кого-то режем; рост `5xx` — ошибки |
| `http_latency_p95_ms` | p95 времени приложения | > 200 мс — перегруз или медленная ручка |
| `sqlite_wal_size_bytes` | размер `-wal` | растёт без отката — чекпойнт не справляется |
| `sqlite_ms` | отклик `SELECT 1` | > 50 мс — диск/локи |
| `symbols_count` / `custom_symbols_count` | монет в списке | `custom` растёт без остановки — флуд `/add` |
| `rss_bytes` | память процесса | > 500 МБ — утечка (смотреть рост между рестартами) |
| `uptime_sec` | секунд с запуска | прыгает вниз сам — процесс падает и рестартует |

`/api/health` дополнительно несёт `clients`, `rss_bytes`, `sqlite_ms`,
`wal_bytes`, `live_exchanges` — для быстрой диагностики руками.

## Ручки управления нагрузкой (переменные окружения)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LIQSCOPE_WS_MAX_CLIENTS` | `400` | кап сокетов процесса (лишним — close 1013 + строка в лог) |
| `LIQSCOPE_RATE_LIMIT` | `1` | `0` — выключить лимитер приложения (только на время `load_test.py`) |
| `LIQSCOPE_TRUSTED_PROXIES` | `127.0.0.1,::1` | кому верить в `X-Forwarded-For` (свой nginx; CIDR можно) |
| `LIQSCOPE_API_CACHE` | `1` | `0` — выключить кэш API (тесты гоняют с нулём) |

Лимиты приложения (поверх nginx): `/ws` — 5 коннектов/минуту с IP
(залогиненным 30); мутирующие `POST /api/*` — 60/10 минут с IP
(залогиненным 600). Мониторинг и GET не режутся. Залогиненность —
по cookie `liqscope_sid`.

## База

`accounts.db`: WAL + `synchronous=NORMAL` + `journal_size_limit=64M`,
фоновый `wal_checkpoint(TRUNCATE)` раз в 10 минут. Резервная копия —
systemd timer (см. `BACKUP.md`): `sqlite3 .backup`, не копирование файла.

## Кэш ответов

* `/api/stats` — 5 с в памяти (считается проходом по всем событиям);
* `/api/health` — 5 с;
* `/api/digest`, `/api/digest/today` — 30 с + сброс при публикации;
* дайджесты и статьи — `Cache-Control: public, max-age=60`.

`proxy_cache` в nginx для `/` и `/terminal` осознанно НЕ включён:
страницы персонально рендерятся под язык (cookie/заголовок), ключ
кэширования получился бы хрупким, а рендер стоит ~1 мс — FastAPI
тянет тысячи таких RPS без прокси-кэша. Вернуться к вопросу при
устойчивых > 500 RPS на страницах.

## Стресс-тест

```bash
# на стенде с выключенным лимитом (иначе 50 коннектов с одного IP — флуд):
LIQSCOPE_RATE_LIMIT=0 ... (перезапуск стенда)
python3 tools/load_test.py --ws 50 --rps 100 --seconds 60
```

Цели: p95 < 200 мс, 0 обрывов WS, RSS < 500 МБ. Замер 27.09.2026
(песочница, демо-режим): p95 4.0 мс, обрывов 0, RSS 80 МБ.

## Когда станет тесно одному воркеру

Признаки: `ws_clients_total` упирается в кап, p95 ползёт за 200 мс при
свободной базе, RSS растёт. План:

1. Поднять кап (`LIQSCOPE_WS_MAX_CLIENTS`) и лимит nginx `limit_conn` —
   если упёрлись только в них.
2. Для `--workers 4`: сначала вынести общее состояние из памяти процесса —
   `Hub.broadcast` (сделать Redis Pub/Sub; интерфейс уже асинхронный),
   `RateLimiter` (заменить бэкенд на Redis), секундные корзины метрик.
   Без этого воркеры будут жить каждый своей жизнью: лимиты ×4,
   рассылки только своим клиентам.
3. SQLite держит ~1000 DAU; дальше — Postgres (отдельная задача, не этот
   раунд).
