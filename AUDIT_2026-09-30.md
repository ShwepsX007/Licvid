## Краткое резюме

В локальном аудите не обнаружено подтверждённой SQL-инъекции или XSS в проверенных участках, а также HIGH-находок Bandit. Это статический аудит исходного дерева, а не полноценный pentest: production-сервер, реальные журналы и live endpoints не проверялись. Самый существенный открытый риск — ссылки email-подтверждения, входа и сброса пароля содержат bearer-токены в URL; без SMTP ссылка дополнительно попадает в журнал приложения. Также systemd unit не задаёт непривилегированного пользователя.

## Подтверждённые находки и рекомендации

### AUTH-01 — секретные email-токены попадают в URL и могут оказаться в логах

**Приоритет: средний. Статус: открыта.**

`web_account.py` формирует ссылки `/verify?token=…`, `/email-login?token=…`, `/reset?token=…` и `/attach?token=…` (около строк 280–303). Клиент страницы сброса также читает токен из query string и вызывает GET `/api/auth/email/token?token=…` (`static/account.js:6155–6176`). При отключённом SMTP код намеренно пишет полную ссылку для ручной выдачи в application log (`web_account.py:296–303`); это поведение задокументировано в `deploy/licvid.service:65–69`. Токены email-flow и session-токены хранятся в базе в исходном виде (`accounts.py`, таблицы token/session).

**Воздействие:** обладатель ещё действующего токена может воспользоваться соответствующей операцией. Это создаёт дополнительные места хранения секрета — access/error-журналы, journal и резервные копии БД. Не установлено, что посторонний действительно имеет доступ к production-журналам или БД; фактические журналы не проверялись. Настроенная в примере Nginx политика `Referrer-Policy: strict-origin-when-cross-origin` уменьшает утечку полного URL на внешние origin, но не скрывает URL от собственных access-логов и same-origin запросов.

**Рекомендации:** не выдавать bearer-ссылку в общем журнале (для ручного сценария использовать отдельный защищённый канал); исключить токены из access-логов; передавать токен из URL-фрагмента в POST body, не запрашивать его через GET; хранить в БД только криптографический digest токена и искать/сверять по digest. Существующий ручной fallback не менялся, чтобы не сломать предусмотренный процесс при отсутствии SMTP.

### DEPLOY-01 — unit приложения по умолчанию работает с правами root

**Приоритет: средний. Статус: открыта.**

В `deploy/licvid.service:6–10,90` заданы рабочий каталог и запуск из `/root/Licvid`, но отсутствуют `User=` и `Group=`. Для system-level unit systemd по умолчанию использует root. Файл — шаблон конфигурации; реальный host может использовать override/drop-in, который в репозитории не виден.

**Рекомендация:** запускать приложение от отдельного непривилегированного пользователя, вынести код из `/root`, дать этому пользователю доступ только на чтение кода и минимально необходимые права записи к данным. Перед изменением проверить реальные drop-in, владение каталогами и восстановление сервиса на deployment-хосте. В рамках этого аудита deployment не менялся.

### DEP-02 — диапазон cryptography включал версии с опубликованными advisory

**Приоритет: средний. Статус: исправлено.**

`pip-audit` обнаружил advisory для установленной `cryptography 46.0.7`, включая CVE-2026-69247, CVE-2026-69248 и CVE-2026-69249. Верхняя граница в `requirements.txt` допускала ветку `<47`. Ограничение изменено на `cryptography>=50.0.0,<51`; соответствующая подсказка установки ключей Alchemy в `alchemy_keys.py` обновлена. После обновления `pip-audit` не нашёл известных уязвимостей ни в requirements, ни в проверенном audit-окружении. Это результат сверки с базой advisories на дату аудита, а не гарантия отсутствия будущих CVE.

### WS-01 — отсутствует явная проверка Origin при WebSocket handshake

**Приоритет: низкий. Статус: hardening-рекомендация.**

`server.py:6754–6768` принимает `/ws` до проверки `Origin` и далее связывает клиента с аккаунтом по session cookie. Для персонализированных событий стоит сравнивать Origin с точным allowlist origin приложения. `SameSite=Lax` у cookie смягчает типичный cross-site сценарий в современных браузерах, поэтому только по этой находке эксплуатация не утверждается. Изменений WebSocket-кода не делалось.

### CI-01 — не закреплены версии JS-тестовых зависимостей

**Приоритет: низкий. Статус: открытая рекомендация.**

CI ставит `jsdom` и `ws` через `npm install --no-save` без версий/lockfile для этих test-only пакетов. Версии могут измениться между запусками, что снижает воспроизводимость и повышает риск компрометации цепочки поставки. Рекомендуется объявить их в `devDependencies` и зафиксировать lockfile. `npm audit` установленного во время аудита набора `jsdom`/`ws` сообщил 0 известных уязвимостей; это не заменяет закрепление версий.

### CI-02 — hosted GitHub Actions падает в Python test runner

**Приоритет: средний. Статус: открыта; первопричина не установлена.**

Проверка push-коммита `376ab42717b6cc3a443023eef7b4aa6e2311eaa2` ([run 36777490656](https://github.com/ShwepsX007/Licvid/actions/runs/36777490656)) прошла setup, установку зависимостей и сборку i18n, но шаг `Run tests (one-button runner)` завершился кодом 1 примерно через 9 минут 30 секунд; JS-шаг после этого был пропущен. Локальный проектный runner с чистым venv и свежими разрешёнными версиями из `requirements.txt` (`LIQSCOPE_SECRET=… PYTHON=/tmp/ci-repro/bin/python bash tools/run_tests.sh --python`) прошёл **82/82** Python test-файла. Следовательно, остаётся неразрешённое различие hosted runner / тестовой среды; это не подтверждает, что hosted CI зелёный. Получить лог шага и загруженный artifact из sandbox не удалось: GitHub Actions log/artifact download завершался `EOF`, поэтому определить упавший тест и первопричину невозможно. Требуется открыть run и выяснить упавший test-файл; вслепую менять тесты не следует.

В том же run GitHub сообщил предупреждение о переводе используемых Actions с Node.js 20 на принудительный Node.js 24. Предупреждение не установлено как причина сбоя; стоит обновить Actions до версий с поддержкой текущего runner runtime.

### SEC-01 — CSP не ограничивает выполнение скриптов

**Приоритет: низкий. Статус: рекомендация.**

В `deploy/nginx-liqscope.conf:83–88` заданы полезные заголовки, включая HSTS, `nosniff`, `X-Frame-Options` и `Referrer-Policy`, однако CSP содержит только `frame-ancestors 'self'`. Это не полноценная политика для ограничения скриптов. Значительная часть страниц использует inline scripts/styles, а админский функционал поддерживает HTML-контент, поэтому добавление `script-src` без инвентаризации сломает функциональность. Рекомендуемый путь — сначала `Content-Security-Policy-Report-Only`, затем постепенное введение nonce/hash и проверка доверенного admin HTML.

### SEC-02 — результаты Bandit требуют дополнительной ручной классификации

Bandit завершился с **0 HIGH, 17 MEDIUM и 191 LOW**. В проверенных динамических SQL-участках `accounts.py` и `whale_screener.py` значения передаются параметрами либо SQL-фрагменты ограничены allowlist; подтверждённой SQL-инъекции не найдено. При этом весь оставшийся список MEDIUM/LOW не был разобран индивидуально, поэтому предупреждения сохранены как открытая очередь, а не объявлены ложными срабатываниями.

## Проверенные защитные меры и участки высокого риска

- **Статьи и HTML:** `articles.py:102–211` экранирует обычный текст, экранирует значения HTML-атрибутов и разрешает в Markdown-ссылках только HTTP(S) и одиночный внутренний `/` (не `//` и не `javascript:`). `static/articles.js` вставляет полученный HTML через `innerHTML`, но он строится серверным Markdown-рендерером. Дополнительные payload-проверки подтвердили экранирование сырого `<img ... onerror=...>`, кавычек в `alt` и отказ от `javascript:` URL. В этих проверенных путях XSS не подтверждён.
- **Чат и пользовательский текст:** в рассмотренных выводах поддержки/сообщений пользовательский текст экранируется до вставки. Это выборочная проверка DOM sinks, не полный аудит каждого клиентского шаблона.
- **Изображения:** загрузки ограничены 12 MB и проверяют raster magic bytes; article принимает JPEG/PNG/WebP/GIF, digest/ad-хранилища — JPEG/PNG/WebP. SVG не принимается в этих путях. Маршруты и лимиты проверялись по коду, не через live upload.
- **SQL:** проверенные Bandit-отмеченные запросы используют параметры или allowlist. Другие предупреждения Bandit не следует считать закрытыми до их триажа.
- **Cookie и deployment-шаблон:** unit задаёт `LIQSCOPE_COOKIE_SECURE=1`, приложение требует `LIQSCOPE_SECRET` в production-режиме и привязано к одному worker. Это проверка файлов в Git, а не активной конфигурации сервера.
- **Секреты:** `detect-secrets scan --all-files --no-verify` выдал 77 эвристических совпадений. Просмотренные совпадения относятся к тестовым значениям, документации, публичным chain identifiers/адресам и константам; подтверждённый credential в текущих файлах не установлен. Проверка истории Git не выполнялась, а `--no-verify` означает, что автоматическая онлайн-верификация кандидатов намеренно не запускалась.
- **Финансовые и блокчейн-потоки:** в рамках аудита не менялись Hyperliquid/TRON, ETH/Solana-парсинг и декодирование сумм, CEX-логика, Alchemy-настройки или ручные wallet labels. Live-провайдеры и фактическая экономия CU не проверялись.

## Исправления в CI и зависимости

1. `requirements.txt`: ограничена версия `cryptography` до проверенной ветки `>=50.0.0,<51`; подсказка установки в `alchemy_keys.py` синхронизирована.

## Ограничения аудита

- Не запускались production/live endpoints, браузерный pentest, активная проверка Nginx/systemd на хосте, реальные SMTP-потоки, логи или состояние production-БД.
- 52 проверки, требующие запущенного live server, не выполнялись. Локальные Python-тесты прошли, но hosted GitHub Actions на commit `376ab42` завершился ошибкой в Python runner; его лог недоступен из sandbox, поэтому полный CI нельзя считать зелёным.
- Не сканировалась история Git на случайно опубликованные секреты; secret scan относится к текущим файлам.
- Результаты Bandit MEDIUM/LOW разобраны не полностью; обзор XSS/SQL ограничен приоритетными участками, а не является формальной исчерпывающей проверкой каждого потока данных.
- Проверка advisories и npm audit отражает базы данных на дату запуска и не гарантирует отсутствие неизвестных уязвимостей.
- Рекомендации для systemd, Nginx и логирования относятся к шаблонам в репозитории; реальная конфигурация deployment могла отличаться.
