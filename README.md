# LiqScope Terminal — живой поток ликвидаций

Веб-терминал, который в реальном времени показывает ликвидации фьючерсов
с **Binance, Bybit, OKX, Gate.io, Bitget, HTX и BitMEX**, свечной график монеты и кластеры
ликвидаций поверх свечей.

Ключи API не нужны — используются только публичные WebSocket-каналы бирж.

```
http://<сервер>:8000/          — лендинг (посадочная страница)
http://<сервер>:8000/terminal  — сам терминал
```

## Что было сломано и что исправлено

| Проблема | Причина | Решение |
|---|---|---|
| Не видно графика, нет выбора монет, пустая лента | `static/app.js` вызывал `chart.addCandlestickSeries()` и `series.setMarkers()` — это API **Lightweight Charts v4**, а в `static/lightweight-charts.js` лежит **v5.2.1**, где этих методов нет. Исключение падало в самом начале скрипта и убивало весь фронтенд целиком (поэтому не работало вообще ничего) | Фронтенд переписан на v5 (`chart.addSeries(LightweightCharts.CandlestickSeries, …)`, `LightweightCharts.createSeriesMarkers(...)`) с автоматическим откатом на v4 |
| «Данные не идут» | Сервер большую часть событий **выдумывал** (`liquidation_simulator_task`), а реальные ликвидации читал через опрос буферов бота с постоянно сбрасываемым курсором `last_ts`; цены были захардкожены (BTC = 78 450) | Симулятор выключен (только `LIQSCOPE_DEMO=1`). Ликвидации идут напрямую из публичных WS бирж, цены и свечи — настоящие |
| Всего 6 монет | Список был захардкожен в `server.py` | Список монет подтягивается с биржи автоматически (топ-N USDT-перпетуалов по обороту за 24 ч), по умолчанию 40, настраивается `LIQSCOPE_SYMBOLS_LIMIT`. В интерфейсе — поиск по монете |
| Непонятно, почему нет данных | Нет диагностики | Появился `GET /api/health` и индикаторы бирж в шапке: видно, кто подключён, сколько событий пришло и с какой ошибкой отвалился источник |
| Hyperliquid постоянно отваливается («соединение обрывается») | Ping `{"method":"ping"}` отправлялся только в ветке 30-секундного простоя сокета (`asyncio.TimeoutError`), а на активной ленте `trades` топ-40 монет простоя не бывает — пинг не уходил вовсе, и биржа закрывала «молчащее» соединение через ~60 с | Пинг шлётся отдельной heartbeat-задачей раз в 50 с **независимо от входящего потока** (как в официальном python-sdk); отправки подписок и пингов сериализованы через `asyncio.Lock` |
| Hyperliquid «висит мёртвым» / обрывается, хотя `--bisect` проходит 23/23 | Три причины: (1) тихо потерянный TCP («зомби»-сокет: обрыв на CF-эдже/NAT/маршруте) не отличался от тихой ленты — `receive()` вечно таймаутил, а `send(ping)` писал в буфер без ошибок, и слушатель никогда не переподключался; (2) backoff супервайзера сбрасывался после любого, даже 2-секундного «успешного» коннекта — долбёжка переподключениями, за которую HL отвечает RST; (3) зависший WS-клиент браузера безлимитно ждал `drain()` внутри фан-аута ликвидаций и подвешивал читателя биржи (зонд клиентов не имеет, поэтому проходил) | Сторож в heartbeat-задаче: если от HL нет **никаких** входящих (ни pong, ни ленты) дольше `LIQSCOPE_HL_STALE_SEC` — соединение принудительно закрывается с громкой причиной в логе, супервайзер переподключается; backoff сбрасывается к минимуму только после соединения, прожившего ≥ 180 с; `Client.send` ограничен 5 с — зависший клиент выбрасывается вместо подвешивания фидов. Долгая проверка канала: `tools/check_hyperliquid.py --soak` (те же подписки + пинги, при обрыве показывает код закрытия и время жизни; код выхода 0/4 — удобно для cron) |
| Hyperliquid «подключается, но ликвидаций нет» / поток стартует минутами | Слушатель подписывался на 40 монет **последовательно, дожидаясь `subscriptionResponse` на каждую по 2.5 с**: пока биржа молчала по одной монете, вся фаза подписок вставала (до 100 с), `connected` в `/api/health` всё это время был `false`, а неподтверждённая подписка не повторялась вовсе. Плюс пинг уходил лишь раз в 50 с при пороге обрыва 60 с, а на подписку HL отдаёт срез последних сделок — каждое переподключение заново вбрасывало в ленту старые ликвидации | Слушатель пересобран на три задачи: **чтение сокета** (единственный `receive()`), **подписки** отдельной задачей (темп ~12/с, без ожидания ответа; неподтверждённые повторяются до 3 раз и это видно в health) и **heartbeat** (пинг раз в 20 с по документации биржи + сторож зомби-сокета). `connected` ставится сразу после рукопожатия. Срез истории отсеивается по возрасту (`LIQSCOPE_HL_FRESH_SEC`). HL ходит через **отдельную сессию** со своим коннектором и без общего `ClientTimeout(total=20)`, а `universe` берётся одноразовой сессией — боевой пул REST/OI/свечей больше не соседствует с биржевым сокетом. В `/api/health` для `hyperliquid` видно `hl_subs_sent/hl_subs_acked/hl_pings/hl_pongs/hl_last_inbound_sec/hl_skipped_stale` — сразу ясно, где затык: нет сокета, нет подтверждений или нет входящих |
| Hyperliquid закрывает сокет кодом `1000` через 1-4 с после начала подписок — и в бою, и в «голом» клиенте, при любом User-Agent и таймауте | `_hyperliquid_load_universe()` приводил имена монет к верхнему регистру, а `hl_coin_map` обещал «оригинальный регистр universe». В итоге дешёвые токены уходили в подписку как `KPEPE`/`KSHIB` вместо биржевых `kPEPE`/`kSHIB`: HL на неизвестное имя отвечает ошибкой и **закрывает всё соединение**, поэтому из-за одной монеты молчал весь поток. Подтверждено на бою: `close_code=1000`, `hl_subs_sent=14, hl_subs_acked=10` | Регистр `universe` больше не трогается (регрессия закрыта тестом на `kPEPE`). Плюс защита: монета, на которую биржа ответила ошибкой, отключается сразу, а монета, после подписки на которую сокет стабильно умирает, — после `LIQSCOPE_HL_COIN_STRIKES` срывов; отключенные видны в `/api/health` → `hl_coins_banned`. Вручную исключить монету можно без правки кода: `LIQSCOPE_HL_SKIP_COINS=kPEPE,SHIB`. Виновника по имени называет `tools/hl_find_killer.py` |

## Быстрый деплой на сервер

```bash
cd /root/LiqScope
git pull                                  # забрать обновление
pip install -r requirements.txt           # fastapi, uvicorn, aiohttp
sudo systemctl restart liqscope
sudo journalctl -u liqscope -f              # смотреть логи
```

Проверка, что данные реально идут:

```bash
curl -s localhost:8000/api/health | python3 -m json.tool
curl -s "localhost:8000/api/liquidations?limit=5" | python3 -m json.tool
```

В `/api/health` для каждой биржи видно `connected`, `events`,
`seconds_since_event` и `last_error`.

### systemd-юнит (пример)

Готовый файл: [`deploy/liqscope.service`](deploy/liqscope.service)

```ini
[Unit]
Description=LiqScope Liquidation Terminal
After=network-online.target

[Service]
WorkingDirectory=/root/LiqScope
Environment=LIQSCOPE_SYMBOLS_LIMIT=40
Environment=LIQSCOPE_EXCHANGES=binance,bybit,okx,gate,bitget,htx,bitmex,hyperliquid,dydx,kraken,bitfinex
ExecStart=/usr/bin/python3 -m uvicorn server:app --host 0.0.0.0 --port 8000
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Установка:

```bash
sudo cp deploy/liqscope.service /etc/systemd/system/liqscope.service
sudo systemctl daemon-reload
sudo systemctl enable --now liqscope
```

## Как данные попадают на экран (задержки)

```
биржа ──WS──► market_feed ──callback──► server ──WS──► браузер ──► график
```

| Поток | Источник | Как часто | Что обновляет |
|---|---|---|---|
| **Тики** | Binance combined `?streams=<sym>@aggTrade` → Binance raw + SUBSCRIBE → Bybit `publicTrade` | **каждая сделка**, без буферизации | цену и свечу открытого графика — сразу, тем же тиком |
| Ликвидации | 8 бирж, WS | **каждое событие**, сразу | лента, маркеры, кластеры |
| Свеча/объём | Binance `kline_1m` | ~250 мс | авторитетный объём свечи; цену не трогает, если тик свежее |
| Цены всех монет | из тиков и `kline_1m` | 1 с | подписи цен у монет |
| Статистика | агрегаты в памяти | 2 с | шапка, топ монет |
| История свечей | REST Binance → Bybit → OKX | 15 с | сверка серии с биржей |

Источник тиков выбирается сам: если сокет открылся, но за 20 секунд не
пришло ни одной сделки, движок переключается на следующий источник и пишет
об этом в лог (`[ticks] ... подключились, но сделок нет`). Активный источник
виден в `/api/health` → `tick_source`. Свечи после этого запрашиваются
с той же биржи, что и тики (`kline_source_preferred`), чтобы цена на
графике не расходилась с последней сделкой.

Порядок источников фиксируется через `LIQSCOPE_TICK_SOURCE` — например,
`LIQSCOPE_TICK_SOURCE=bybit`, если на вашем сервере Binance принимает
подписку, но рыночные данные не присылает (встречается на части хостингов).

Тики идут только по монетам, чьи графики сейчас открыты («горячие» монеты):
сервер подписывается и отписывается на лету через `SUBSCRIBE`/`UNSUBSCRIBE`,
поэтому трафик не зависит от размера списка монет.

В шапке графика видно `⚡ тики: N · задержка X мс` — это реальная задержка
между временем сделки на бирже и отрисовкой у вас в браузере.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LIQSCOPE_SYMBOLS_LIMIT` | `40` | сколько монет держать в списке (топ по обороту) |
| `LIQSCOPE_EXCHANGES` | `binance,bybit,okx,gate,bitget,htx,bitmex,hyperliquid,dydx,kraken,bitfinex` | какие биржи слушать |
| `LIQSCOPE_DYDX_WS` | `wss://indexer.dydx.trade/v4/ws` | адрес индексера dYdX v4 |
| `LIQSCOPE_DYDX_SUB_GAP_MS` | `550` | пауза между подписками dYdX (индексер разрешает 2/с на пару канал+id) |
| `LIQSCOPE_DYDX_REST` | `https://indexer.dydx.trade` | откуда брать список рынков dYdX: подписываемся только на существующие тикеры |
| `LIQSCOPE_KRAKEN_REST` | `https://futures.kraken.com/derivatives/api/v3` | то же для продуктов Kraken Futures |
| `LIQSCOPE_KRAKEN_WS` | `wss://futures.kraken.com/ws/v1` | адрес Kraken Futures |
| `LIQSCOPE_KRAKEN_PING_SEC` | `25` | интервал пинга Kraken Futures (обрывает сокет после 60 с молчания) |
| `LIQSCOPE_BITFINEX_WS` | `wss://api-pub.bitfinex.com/ws/2` | адрес Bitfinex |
| `LIQSCOPE_BITFINEX_PING_SEC` | `20` | интервал пинга Bitfinex |
| `LIQSCOPE_LIQ_FRESH_SEC` | `120` | насколько свежие события из подписочного среза новых бирж пускать в ленту |
| `LIQSCOPE_NEW_SOURCE_LOG_SEC` | `60` | как часто dYdX/Kraken/Bitfinex/0xArchive отчитываются в лог о подписках и ликвидациях |
| `LIQSCOPE_DEMO` | `0` | `1` — синтетический поток для проверки интерфейса без бирж (в шапке загорится бейдж `DEMO`) |
| `LIQSCOPE_HISTORY_MAX` | `60000` | сколько событий держать в памяти |
| `LIQSCOPE_HISTORY_FILE` | `data/liq_history.jsonl` | файл истории ликвидаций (JSONL, append). Пустая строка / `0` / `off` — не писать на диск |
| `LIQSCOPE_HISTORY_TTL_HOURS` | `24` | сколько часов истории держать при загрузке с диска и урезании файла |
| `PORT` | `8000` | порт при запуске `python3 server.py` |
| `LIQSCOPE_TICK_SOURCE` | `binance,binance-raw,bybit` | порядок источников тиков (по ним считается **CVD**). Доступны также `dydx`, `kraken`, `bitfinex`, `hyperliquid` — например `binance,bybit,dydx,kraken,bitfinex,hyperliquid`. Если известно, что Binance на этом сервере не отдаёт сделки — поставьте `bybit`, чтобы не терять 40 с на его переопрос после рестарта |
| `LIQSCOPE_TICK_MIN_GAP_MS` | `0` | минимальный зазор между тиками графика по монете (`0` = слать каждый тик; поставьте, например, `40`, если хочется беречь трафик) |
| `LIQSCOPE_HL_PING_SEC` | `20` | интервал heartbeat-пинга Hyperliquid. Биржа закрывает соединение, если 60 с ничего в него не послала (docs → «Timeouts and heartbeats»); 20 с — трёхкратный запас до порога |
| `LIQSCOPE_HL_FIRST_PING_SEC` | `10` | когда слать первый пинг после подключения (не ждём полного интервала — пока встают подписки, лента молчит) |
| `LIQSCOPE_HL_STALE_SEC` | `80` | сторож зомби-сокетов HL: если от биржи нет ничего (ни pong, ни ленты) дольше этого — соединение принудительно закрывается и переподключается |
| `LIQSCOPE_HL_SUB_GAP_MS` | `80` | пауза между подписками на монеты (темп ~12/с: топ-40 встаёт за ~3 с без всплеска, за который гейтвей рвёт соединение) |
| `LIQSCOPE_HL_ACK_SEC` | `4` | сколько ждать `subscriptionResponse` перед повтором подписки |
| `LIQSCOPE_HL_SUB_TRIES` | `3` | сколько раз повторять неподтверждённую подписку, прежде чем сдаться по монете |
| `LIQSCOPE_HL_FRESH_SEC` | `120` | сделки старше этого считаются срезом истории (на подписку HL отдаёт последние сделки) и в ленту не идут |
| `LIQSCOPE_HL_SKIP_COINS` | — | монеты, которые не нужно подписывать на HL (через запятую): `kPEPE,SHIB`. Спасает, если биржа рвёт соединение на конкретном имени |
| `LIQSCOPE_HL_COIN_STRIKES` | `2` | сколько срывов соединения «простить» монете, прежде чем отключить её совсем |
| `LIQSCOPE_HL_SHARED` | `0` | `1` — вести HL через общую боевую сессию вместо отдельной (только для A/B-диагностики, см. `tools/hl_standalone_test.py`) |
| `LIQSCOPE_HL_WS` / `LIQSCOPE_HL_REST` | `wss://api.hyperliquid.xyz/ws` / `https://api.hyperliquid.xyz` | адреса биржи: тестнет (`wss://api.hyperliquid-testnet.xyz/ws`), свой узел или локальная псевдо-биржа для тестов |
| `LIQSCOPE_HL_UA` | `LiqScope-Terminal/4.1` | User-Agent для сокета и REST Hyperliquid |
| `LIQSCOPE_LIQ_FLUSH_MS` | `0` | `0` = каждая ликвидация уходит немедленно; `>0` — склеивать в пачки |
| `LIQSCOPE_PRICE_INTERVAL_MS` | `1000` | как часто обновлять таблицу цен |
| `LIQSCOPE_STATS_INTERVAL_MS` | `2000` | как часто пересчитывать статистику |

## API

| Метод | Описание |
|---|---|
| `GET /` | лендинг с живой статистикой и ссылкой в терминал |
| `GET /terminal` | сам терминал |
| `GET /api/symbols` | дефолтный топ монет (по обороту 24ч) + добавленные вручную; цены, обороты, `volAvg7d` (средний оборот за неделю), ликвидации за 24 ч |
| `GET /api/symbols/search?q=GRAM` | поиск пары по ПОЛНОМУ каталогу бирж (не только по топу): можно найти `GRAM`, `GRAM_USDT`, `gram/usdt` |
| `POST /api/symbols/add?symbol=GRAM` | добавить пару из каталога в список и на график (404, если пары нет ни на одной бирже; `force=true` — добавить вслепую) |
| `GET /api/klines?symbol=BTC_USDT&timeframe=5` | свечи (1/5/15/60/240 мин), в т.ч. для пар не из топа |
| `GET /api/liquidations?symbol=&exchange=&min_usd=&limit=` | история ликвидаций |
| `GET /api/stats?symbol=` | агрегаты: лонги/шорты за 1м/5м/15м/30м/1ч/4ч/24ч, топ монет, разрез по биржам |
| `GET /api/oi?symbol=BTC_USDT` | открытый интерес: текущий тотал по живым ногам + изменения m1/m5/m15/m30/h1/h4/h24 (m1 — по живым опросам) |
| `GET /api/health` | состояние источников, `ticks_seen`, `hot_symbols`, `seconds_since_last_tick`, каталог для поиска |
| `WS /ws` | живой поток: `init`, `liqs`, `tick`, `candle`, `candles`, `prices`, `stats` |

Клиент шлёт в сокет `{"action":"sub","symbol":"BTC_USDT","chart":"SOL_USDT","tf":5}` —
`symbol` — фильтр ленты, `chart` — символ графика (они могут отличаться;
раньше график неявно совпадал с фильтром, из-за чего при «🌐 ВСЕ» живые
тики шли не по той монете).

## Источники данных

| Биржа | Канал | Как определяется сторона / объём |
|---|---|---|
| Binance USDⓈ-M | `!forceOrder@arr` | `S=SELL` → ликвидирован **LONG** |
| Bybit linear | `allLiquidation.<SYMBOL>` | `S=Buy` → **LONG** (Bybit отдаёт сторону позиции) |
| OKX SWAP | `liquidation-orders` (instType=SWAP) | `posSide=long` → **LONG**, размер × `ctVal` |
| Gate.io USDT | `futures.public_liquidates` | `size < 0` → **LONG**, объём = `size × quanto_multiplier` |
| Bitget UTA | `liquidation` (instType=usdt-futures) | `side=buy` → **LONG**, `amount` уже в USDT |
| HTX (Huobi) USDT-M | `public.*.liquidation_orders` (gzip) | `direction=sell` → **LONG**, `trade_turnover` в USDT |
| BitMEX | таблица `liquidation` | `side=Sell` → **LONG**; учитываем только `action=insert`, размер переводим из контрактов через `underlyingToPositionMultiplier` (инверсные `XBTUSD`: 1 контракт = 1 USD) |
| dYdX v4 | `v4_trades` на каждый тикер | сделки с `type=Liquidated` и `Deleveraged` (принудительное закрытие страховым фондом); тейкер `SELL` → **LONG**. Подписка по тикеру вида `BTC-USD`, карта строится из нашего списка монет. Индексер разрешает 2 подписки в секунду на пару «соединение+канал+id», поэтому темп подписок ограничен `LIQSCOPE_DYDX_SUB_GAP_MS` (по умолчанию 550 мс), а на подписку биржа отдаёт срез последних сделок — он отсеивается по возрасту |
| Kraken Futures | `trade` (публичный) | у сделки поле `type`: `liquidation` (движок) и `termination` (принудительное закрытие — считаем ликвидацией, `kind=termination`); `fill`/`block` не считаем. Тейкер `sell` → **LONG**. Продукты вида `PF_XBTUSD`; подписка шлётся **по одному продукту за раз**, потому что на `Invalid product id` Kraken закрывает всё соединение. Пинг раз в `LIQSCOPE_KRAKEN_PING_SEC` (25 с) — биржа рвёт сокет после 60 с молчания |
| Bitfinex | `status` c ключом `liq:global` | **одна подписка на всю биржу**: в ленте позиции, закрытые по ликвидации. `chanId` берётся из подтверждения подписки, кадры чужих каналов и `"hb"` игнорируются. Сторона — из знака `AMOUNT` (`+` → **LONG**), цена — `LIQUIDATION_PRICE` (индекс 11), объём — `|AMOUNT|`. Спот-символы отсеиваются и это видно в `/api/health` → `bitfinex_skipped_other`. Пинг раз в `LIQSCOPE_BITFINEX_PING_SEC` (20 с) |
| Hyperliquid | `trades` на каждую монету | только сделки с объектом `liquidation`; тейкер `A` (продажа) → **LONG**. Маппинг монет — из `universe` (`POST /info {"type": "meta"}`), дешёвые токены с префиксом `k` (`kPEPE`). Срез истории, который биржа отдаёт на подписку, в ленту не идёт (`LIQSCOPE_HL_FRESH_SEC`) — иначе каждое переподключение показывало бы вчерашние ликвидации как новые |

Отключить лишние: `LIQSCOPE_EXCHANGES=binance,bybit,bitget`.

#### Hyperliquid через 0xArchive (по API-ключу, необязательно)

Сам HL ликвидаций не публикует, но их публикует индексатор
[0xArchive](https://0xarchive.io/hyperliquid). У него два пути — REST и WS.

**Замер на боевом сервере 14.09.2026** (один бесплатный ключ, `BTC ETH SOL`,
полчаса):

| путь | результат |
|---|---|
| `GET /v1/hyperliquid/liquidations/{coin}` за 24 ч | **1118 ликвидаций** (BTC 457 / $2,4 млн, ETH 661 / $3,7 млн), свежайшая — 0 с назад |
| WS-канал `liquidations` за 1800 с | **0 кадров `type=data`**: 75 кадров = 3 `subscribed` + 72 наших же `pong` |

Подписки подтверждались, ошибок и `gap_detected` не было — канал просто
ничего не отдаёт. Поэтому **рабочий путь — опрос REST**
(`LIQSCOPE_OXA_MODE=rest`, по умолчанию), а WS оставлен как резерв и
отлаживается отдельно. Строка REST выглядит иначе, чем WS-кадр: полей
`is_liquidation`/`px`/`sz`/`time` там нет, вместо них
`liquidated_user`/`liquidator_user`/`direction`/`price`/`size`/`timestamp`,
и сторона берётся из `direction` (`Long`/`Short`), а не из тейкера.

Ликвидации отдаются **построчно по монете**, поэтому бесплатный тариф
(10 подписок, 2 соединения, **50 000 кредитов в месяц на ключ**, 1 запрос =
минимум 1 кредит) покрывает мало монет. Бюджет складывается ключами —
источник держит **по одному потоку на ключ** и делит список монет между
ними:

```ini
# /etc/systemd/system/licvid.service — несколько аккаунтов через запятую
Environment=LIQSCOPE_OXA_KEYS=0xa_ключ1,0xa_ключ2,0xa_ключ3
```

Без ключей источник не стартует вовсе и пишет причину в `/api/health` — по
умолчанию проект остаётся полностью «без ключей». В ленте событие помечено
биржей **hyperliquid**: ликвидация произошла там, 0xArchive только транспорт.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `LIQSCOPE_OXA_KEYS` | — | ключи через запятую (или `;`); один ключ можно задать в `OXARCHIVE_API_KEY` |
| `LIQSCOPE_OXA_MODE` | `rest` | `rest` (рабочий), `ws` или `both` |
| `LIQSCOPE_OXA_COINS_PER_KEY` | `2` | монет на ключ в режиме `rest` |
| `LIQSCOPE_OXA_POLL_SEC` | `120` | как часто опрашивать каждую монету |
| `LIQSCOPE_OXA_CREDITS` | `50000` | месячный бюджет кредитов на ключ |
| `LIQSCOPE_OXA_SUBS_PER_KEY` | `10` | монет на ключ в режиме `ws` |
| `LIQSCOPE_OXA_FRESH_SEC` | `300` | окно свежести событий |
| `LIQSCOPE_OXA_PING_SEC` | `25` | интервал пинга (только `ws`) |
| `LIQSCOPE_OXA_REST` | `https://api.0xarchive.io/v1/hyperliquid` | адрес REST |
| `LIQSCOPE_OXA_WS` | `wss://api.0xarchive.io/ws` | адрес WS |

**Главное ограничение — не подписки, а кредиты.** Один запрос стоит минимум
1 кредит, месяц на Free — 50 000 кредитов на ключ, то есть ~69 запросов в час
на ключ. Отсюда жёсткая арифметика:

| ключей | опрос раз в 30 с | 60 с | 120 с | 300 с |
|---|---|---|---|---|
| 1 | 0 | 1 | **2** | 5 |
| 2 | 0 | 2 | **4** | 10 |
| 4 | 0 | 4 | **8** | 20 |
| 6 | 0 | 6 | **12** | 30 |

(монет суммарно на все ключи; жирным — дефолт)

Опрос раз в 60 с одним ключом покрывает **одну** монету, а не десять. Дефолт
подобран так, чтобы укладываться одним ключом: 2 монеты × 30 запросов/ч ×
720 ч = 43 200 кредитов из 50 000.

Настройка сверх бюджета не выжигает ключ молча: `oxa_coins_for_budget()`
считает, сколько монет влезает, лишнее обрезается, а в лог уходит
предупреждение с готовым значением `LIQSCOPE_OXA_POLL_SEC`, при котором
запрошенное число монет влезло бы целиком (5 монет — 259 с, 10 — 518 с).

Окна опроса перекрываются на 30 с, а повторы отсеиваются по `trade_id`,
поэтому редкий опрос не теряет события между запросами. Расход виден в
`/api/health`: `oxa_credits_planned` (по настройкам, сразу) и
`oxa_credits_month_eta` (по факту запросов) против `oxa_credits_budget`.
Фактический прогноз появляется только после полного цикла опроса —
экстраполяция первых секунд врёт на порядки.

В `/api/health` для `oxa` видно `oxa_keys`, `oxa_mode`, `oxa_requests`,
`oxa_dupes`, `oxa_credits_planned/month_eta/budget`,
`oxa_coins_clamped_from`, `oxa_subs_acked/total`,
`oxa_frames`, `oxa_liquidations`, `oxa_skipped_stale/other` и
`oxa_coins_uncovered` — сколько монет не влезло в квоту ключей. Отдельно
считается `oxa_frame_kinds` (типы принятых кадров): если кадры идут, а строк
ликвидаций нет, в лог уходит предупреждение с этими типами — «ноль
ликвидаций» тогда отличим от незнакомого формата кадра.

Проверить доступ своими глазами: `python3 tools/oxa_probe.py --selftest`,
затем `--rest BTC ETH --hours 24` (сколько событий вернёт REST) и
`BTC ETH SOL 1800` (идёт ли что-нибудь в WS).

Проверить ключ до включения: `tools/oxa_probe.py` (см. ниже).

Внутренности каждого нового канала видны в `/api/health`: `dydx_trades_seen` /
`dydx_subs_acked`, `kraken_trades_seen` / `kraken_subs_acked`, у Bitfinex —
`bitfinex_rows_seen`, `bitfinex_liq_long` / `bitfinex_liq_short` и
`bitfinex_skipped_other`. По ним сразу видно разницу между «подключён, но
ликвидаций на этой бирже не было» и «канал сломался».

#### Hyperliquid: ликвидаций в публичном API нет, OI — есть

Замер на боевом сервере (13.09.2026, 8403 кадра, 18144 сделки): **ноль** сделок
с объектом `liquidation`, набор полей всегда `coin, hash, px, side, sz, tid,
time, users`. Публичный API HL публикует ликвидации только внутри **личной**
ленты кошелька (`userFills`), глобального канала нет. Поэтому HL остаётся в
проекте как источник **открытого интереса** (`POST /info {"type":
"metaAndAssetCtx"}` → `openInterest` рядом с `markPx`) и не даёт ликвидаций.

Единственный известный способ получить глобальные ликвидации HL — индексатор
[GoldRush (Covalent)](https://goldrush.dev/docs/goldrush-hyperliquid/overview):
`wss://hypercore.goldrushdata.com/ws?key=<GOLDRUSH_API_KEY>` с подпиской
`{"method":"subscribe","subscription":{"type":"liquidationFills"}}` — один
канал на всю биржу, в каждом кадре `fills` и непустой `liquidation`
(`liquidatedUser`, `markPx`, `method`). Но это **платный API-ключ** (1 кредит в
минуту), что ломает принцип «публичные потоки без ключей», поэтому в проект он
не встроен. Если ключ появится — интеграция сводится к одному слушателю:
адрес вместо `LIQSCOPE_HL_WS`, ключ в query-строке, разбор `fills`
(`coin/px/sz/side/time` + `liquidation`) — парсер уже есть
(`parse_hyperliquid_msg` принимает и такой набор полей).

### Почему нет Coinbase, KuCoin и BingX

| Биржа | Почему |
|---|---|
| **Coinbase** | На спотовой бирже ликвидаций не бывает; у Coinbase International (деривативы) в публичном WS каналов `liquidation` нет |
| **KuCoin Futures** | Публичные топики — стакан, сделки, тикер, funding. Ликвидации есть только в приватном канале своих ордеров (`tradeType=liquid`) |
| **BingX** | В публичном WS перпетуалов каналов ликвидаций нет (только стакан/сделки/свечи/тикер) |

Если очень нужен KuCoin — его можно добавить через платный агрегатор
или через приватные ключи (только свои позиции), но «как у всех остальных»,
из публичного потока — нельзя. (Hyperliquid так когда-то и считался
закрытым, но оказалось, что его `trades` помечают ликвидации объектом
`liquidation` — поэтому он теперь восьмой в списке.)

Цены и свечи: WS `kline_1m` Binance, история — REST Binance → Bybit → OKX
(что первым ответит). Если Binance недоступен из вашей страны, терминал
автоматически перейдёт на Bybit/OKX.

## Интерфейс

- **Выбор монеты — выпадающий список, как на биржах.** Сервер раз в час
  собирает ПОЛНЫЙ каталог USDT-перпетуалов с Binance, Bybit, OKX, Gate и
  Bitget (несколько тысяч пар) и сортирует его по обороту за 24 часа. В
  селекторе показывается только верх (`LIQSCOPE_SYMBOLS_LIMIT`, по умолчанию
  40) — поэтому, например, свежей пары `GRAM/USDT` могло не быть в списке,
  хотя она есть на Binance. Кнопка «Монета» показывает только выбранную
  пару (или **🌐 ВСЕ**); клик открывает вертикальный список: «ВСЕ» +
  монеты с суммой ликвидаций за 24ч, 📈 — что сейчас на графике, ★ —
  добавленные вручную. Клик — выбрать пару (лента + график), **Shift+клик** —
  только график. Поиск по коду: введите `GRAM` — терминал найдёт пару в
  полном каталоге и по кнопке **＋ Добавить** откроет её график и добавит в
  список (такие монеты помечаются ★ и не выпадают из списка при обновлении
  топа).
- **Клик по монете в «Прямом эфире ликвидаций»** открывает график этой пары
  (колонка подсвечена и показывает 📈 при наведении). Остальная часть строки
  по-прежнему открывает окно с деталями ликвидации.
- **Фильтр «Мин. объем»** — выпадающая панель: быстрые кнопки ($1K…$500K)
  и ручной ввод порога (Enter или «OK»). Порог запоминается в браузере.
- **Фильтр «Биржа»** — выпадающая панель с чекбоксами: можно включить/выключить
  любую биржу отдельно; кнопки «Все»/«Ничего» — включить или выключить сразу всё.
  Выбор запоминается в браузере.
- **Прямоугольники ликвидаций** рисуются прямо на свече, в точке цены
  события, и прижимаются к диапазону `low..high` этой свечи. Биржи отдают
  цену банкротства — она может уходить далеко от рынка, поэтому без
  ограничения метки «улетали» в пустое поле графика. Если свечи за это
  время в серии нет, событие не рисуется вовсе. Совсем мелкие события
  рисуются чипом без текста; подписи крупных не налезают друг на друга.
- Палитра мелких событий кодирует сторону: ликвидация лонгов —
  **маджента**, шортов — **циан**. Киты красятся по тепловой шкале
  объёма (для BTC: **$100K — жёлтый → $300K → $500K → $1M → ярко-красный**
  ($5M+)), с тёмной подложкой и светящимся ободком, чтобы читались на свече
  любого цвета. Маркеры-«молнии» 🔥 над/под свечой красятся в тот же
  тепловой цвет. Порог кита масштабируется от оборота монеты (см. ниже).
- **Кнопка «🌐 ВСЕ»** переключает только ленту: в эфир идут ликвидации всех
  монет, а график остаётся на выбранной монете (она помечена значком 📈).
  Клик по монете переводит и ленту, и график; **Shift+клик** — только график.
  Выбор графика запоминается в браузере.
- **Профиль ликвидаций** — теперь индикатор прямо на графике, а не плавающая
  панель: горизонтальные полосы от левого края по каждому ценовому уровню
  (как volume profile), ширина полосы = объём ликвидаций на этом уровне за
  видимый период. Лонги — маджента, шорты — циан, у крупных уровней подпись
  суммы. Индикатор учитывает текущий фильтр (монета, биржи, мин. объём),
  пересчитывается при движении/зуме графика и включается/выключается
  кнопкой **📊 Профиль** в шапке графика (состояние сохраняется в браузере).
- **Телефон**: раскладка перестраивается в одну колонку (раньше лента шириной
  430 px выдавливала график до нулевой ширины — из-за этого его не было
  видно), график занимает ~58% высоты экрана и сворачивается кнопкой ▾
  в шапке графика. В ленте на телефоне остаются колонки «Время», «Монета»
  (кликабельная — открывает график), «Тип» и «Сумма»; скрываются только
  «Биржа» и «Цена».
- **Наведение на прямоугольник подсвечивает ленту.** Каждый прямоугольник —
  это кластер ликвидаций одной свечи на одном ценовом уровне (внутри свечи
  6 уровней). Наведите курсор на прямоугольник — в «Прямом эфире» контрастно
  подсветятся именно те события, из которых он собран (остальное затемняется),
  и лента прокрутится к первому. Клик (на телефоне — тап) закрепляет
  подсветку, повторный клик/тап по тому же прямоугольнику или по пустому
  месту — снимает.
- **Регулируемые панели, как на биржах.** Между графиком и лентой есть
  вертикальный разделитель (тянется мышью/пальцем — меняется ширина ленты),
  внутри ленты — горизонтальный (высота блока «Лидеры по ликвидациям»).
  Размеры сохраняются в браузере (`liqscope.layout`) и восстанавливаются после
  F5; на телефоне раскладка фиксированная, разделители скрыты.
- **Разворот графика на весь экран** — кнопка ⛶ в шапке графика (и на телефоне,
  и на компьютере): график раскрывается поверх всего, Esc или повторный клик —
  назад. Удобно рассматривать кластеры на маленьком экране.
- **CVD-треугольники: кто двигает цену.** У каждой свечи считается тейкер-дельта —
  разница объёмов агрессивных покупок (бьют по аску) и агрессивных продаж
  (бьют по биду) от открытия до закрытия свечи, в USDT. Треугольник стоит строго
  в центре тела свечи: **фиолетовый ▲** — преобладали покупатели,
  **оранжевый ▼** — продавцы; размер треугольника и подпись суммы — величина
  перевеса (мелочь рисуется без подписи, слабые сигналы при тесноте
  уступают место сильным). На формирующейся свече треугольник живой (обновляется
  на каждом тике), после закрытия остаётся с финальным значением. В шапке —
  бокс CVD по монете графика (период выбирается кликом), рядом с кнопкой — индикатор
  перевеса текущей свечи («▼ −$158K»). Источники истории
  CVD: **Binance** (поле taker buy volume прямо в kline — любой таймфрейм) →
  **OKX** (публичная статистика `rubik/taker-volume-contract`); у Bybit
  публичной истории тейкер-объёмов нет, но живые сделки с его `publicTrade`
  (флаг стороны тейкера) копятся сервером с момента запуска. Если REST бирж
  недоступен, дельта текущей свечи всё равно считается из тиков — треугольники
  растут на глазах. Поле `cvd_source` в `/api/status` показывает, чья история
  используется.
- **OI-шарики: куда идут деньги.** У каждой свечи считается изменение
  открытого интереса за её время (USD, сумма по биржам с историей).
  Рост — **зелёный шарик над хаем**, падение — **красный под лоем**,
  с отступом от свечи. Цвет — по направлению и тиру: рост от бледно-зелёного
  к кислотному, падение от бледно-красного к интенсивному. Размер и кегль —
  по величине изменения (цифры для BTC): мелочь **<$1M — мини-шарик без цифр**,
  $1M+ — подписанный шарик, $5M+ и $20M+ — всё крупнее и с более сильным
  свечением; слабые при тесноте уступают сильным. Для монет с меньшим
  оборотом тиры ниже (см. ниже). В шапке —
  бокс OI
  по монете графика:
  изменение за выбранный период + суммарный интерес со всех 11 бирж. Источники:
  мгновенный OI опрашивается со всех бирж раз в 30 с, история 5-минуток —
  **Binance** (`openInterestHist`), **Bybit** (`open-interest` 5min),
  **Gate** (`contract_stats`); изменения и шарики считаются только
  по ногам, присутствующим в обоих сравниваемых бакетах, — подключение
  новой биржи не даёт ложных скачков. На лендинге — те же OI-плашки
  по лидеру рынка.
- **Три окошка статистики в шапке.** Вместо десяти карточек 24ч/1ч/5м —
  три бокса: **ликвидации**, **CVD** (по монете графика) и **OI Δ**
  (по монете графика). Клик по боксу открывает меню периода:
  1 мин / 5 / 15 / 30 мин / 1 ч / 4 ч / 24 ч (дефолт — 24 ч, как раньше),
  в каждой строке меню сразу видно значение за этот период. Под значением —
  детали: у ликвидаций сплит лонги/шорты, у CVD — встречные потоки,
  у OI — суммарный интерес. Выбор периода у каждого бокса свой
  и запоминается в браузере (`liqscope.statwin.liq/cvd/oi`).
- **«Крупность» масштабируется от оборота монеты.** Что для BTC пыль,
  для GRAM — кит: поэтому пороги кита ($100K), подписей ($2K), тиров OI
  ($1M/$5M/$20M) и пола шума CVD/OI ($1K) умножаются на отношение
  средненедельного оборота монеты к BTC (кламп 0.001…2, нет данных — 1).
  Сервер каждый час пишет срез оборотов (`data/vol_history.json`, хранится
  ~неделя) и отдаёт среднее в поле `volAvg7d` (`/api/symbols` и WS `init`);
  подсветка кита в ленте считается по монете каждого события отдельно.
- **Окно фигуры: наведи на прямоугольник, треугольник или шарик.** Наведение
  открывает попап с разбором: у кластера ликвидаций — свеча, уровень,
  доминанта, сумма (+ кит), число событий, сплит L/S, биржи (бейдж +
  число событий + сумма по каждой) и движение цены;
  у CVD — направление, сумма и сила относительно p90; у OI — направление,
  сумма и тир с порогом в масштабе монеты; везде строка-пояснение.
  У кластера окно идёт вместе с подсветкой связанных строк в ленте.
  Активная фигура подсвечивается белым кольцом. Клик закрепляет окно
  (димминг): висит, пока не кликнешь по фигуре повторно, мимо неё или
  по крестику. Смена монеты или выключение слоя окно закрывает.
- **Четыре слоя на графике, кнопки в легенде.** «⚡ Ликвидации» —
  прямоугольники ликвидаций (и маркеры китов), «📊 Профиль» — профиль
  объёмов по ценам, «🎯 CVD» — треугольники, «● OI» — шарики открытого
  интереса. Состояние каждой кнопки сохраняется в браузере
  (`liqscope.liqEnabled`, `liqscope.profileEnabled`, `liqscope.cvdEnabled`,
  `liqscope.oiEnabled`). Кнопка прячет только фигуры на графике — цифры
  у кнопок и боксы в шапке продолжают жить своей жизнью.
- **Живые цифры строго у своих подписей.** В верхней плашке у каждого слоя —
  подпись и текущий поток: у «Ликвидации» — сумма и число событий текущей
  свечи, у «📊 Профиль» — объём ликвидаций видимого диапазона, у «CVD» —
  перевес текущей свечи, у «OI» — её изменение OI. Обновляются на каждом
  тике и событии, пусто — приглушённое тире. У цифр ширина по содержимому
  + табличные цифры (все цифры равной ширины) — плотно сидят и не дёргают
  раскладку; на телефоне ячейки текут в строку как в браузере.
  Кнопки свернуть/развернуть прибиты к правому краю легенды.
  Активный слой подсвечен цветом своих фигур (золото/циан/фиолет/зелёный).
- **Попап кнопок слоёв.** Все тумблеры — «⚡ Ликвидации», «📊 Профиль»,
  «🎯 CVD», «● OI» — живут в выезжающей сверху горизонтальной панели,
  её открывает заметная циановая кнопка «☰ Слои» в правом углу — рядом
  с рисованием, свернуть и развернуть; весь угол зафиксирован и не бегает
  за цифрами. Закрытие панели: повторный клик, клик мимо, Esc.
- **Рисование теханализа.** Кнопка ✎ у графика открывает панель: трендовая
  линия, луч, горизонтальный уровень, прямоугольник, уровни Фибоначчи,
  ластик, 4 цвета. Фигуры привязаны ко времени/цене — зум и скролл
  их не сдвигают; хранятся в браузере отдельно по каждой монете.
  Выход — Esc, правая кнопка или ✕.
- **Лидеры не схлопываются.** Раньше при выборе монеты блок «Лидеры»
  показывал только её одну (топ считался по отфильтрованным событиям).
  Теперь `top_coins` в `/api/stats` всегда глобальные — список лидеров
  виден целиком при любом фильтре (фильтр биржи уважаем).
- **История пузырьков переживает F5 и рестарт сервера.** Сервер пишет каждое
  событие в `data/liq_history.jsonl` (JSONL, до `LIQSCOPE_HISTORY_MAX` событий,
  TTL `LIQSCOPE_HISTORY_TTL_HOURS` ч) и восстанавливает её при старте. Клиент при
  загрузке догружает до 2000 событий выбранной пары через
  `GET /api/liquidations?symbol=…` (дедупликация по `id`, без дублей после
  переподключения) и дополнительно кэширует их в IndexedDB на этом устройстве —
  даже если сервер перезапустили с пустым файлом, у пользователя остаётся его
  собственная история. Видимое окно прямоугольников по-прежнему ограничено
  загруженными свечами (~300 баров: 5 ч на 1m, 25 ч на 5m).
- **Языки (i18n)**: выпадающий переключатель языка в шапке терминала и на
  лендинге — русский, английский, китайский, хинди, испанский. Переводы лежат
  в `static/i18n.js` (словари RU/EN/ZH/HI/ES), статический текст помечен
  атрибутами `data-i18n*`, динамический идёт через `LiqScopeI18n.t()`.
  Выбор хранится в localStorage (`liqscope.lang`), по умолчанию — язык
  браузера или русский. Форматы чисел/времени/дат тоже локализованы
  (`Intl` с локалью выбранного языка).

## Диагностика бирж с сервера

```bash
python3 tools/check_exchanges.py            # BTCUSDT, ожидание 10 с
python3 tools/check_exchanges.py ETHUSDT 60 # дольше ждать ликвидации
```

Скрипт проверяет не «открылся ли сокет», а **приходят ли данные** в каждый
канал, которым пользуется терминал: aggTrade, kline_1m, `!forceOrder@arr`,
`publicTrade`, `allLiquidation`, `liquidation-orders`,
`futures.public_liquidates` — плюс REST каждой биржи.

## Диагностика Hyperliquid

Сначала — что говорит сам терминал. Для `hyperliquid` в `/api/health` теперь
видно внутренности канала, и по ним сразу понятно, где затык:

```bash
curl -s localhost:8000/api/health | python3 -c 'import json,sys; \
  print(json.dumps(json.load(sys.stdin)["sources"]["hyperliquid"], indent=2, ensure_ascii=False))'
```

| Поле | Что означает |
|---|---|
| `connected`, `attempts`, `reconnects`, `last_error` | жив ли сокет, сколько было попыток, причина последнего обрыва (код закрытия или текст сторожа) |
| `hl_subs_total` / `hl_subs_sent` / `hl_subs_acked` | сколько монет надо подписать / сколько подписок ушло / сколько биржа подтвердила. `acked < sent` дольше минуты — биржа не принимает подписки (в логе будет строка «не подтвердила подписку») |
| `hl_pings` / `hl_pongs` | наши пинги и ответы биржи. `pongs` отстаёт от `pings` — трубу уже не слышно |
| `hl_last_inbound_sec` | сколько секунд от биржи не было вообще ничего. Растёт выше `LIQSCOPE_HL_STALE_SEC` — сработает сторож |
| `hl_skipped_stale` | сколько сделок отсеяно как срез истории. Растёт, а `events` = 0 — проверьте часы сервера (`timedatectl`): при большом рассинхроне фильтр съест живой поток |
| `events` | сколько ликвидаций дошло до ленты. Это главный признак, что поток реально идёт |
| `hl_coins_banned` | монеты, которые HL не принял и которые слушатель отключил сам. Пустой список — норма |

Дальше — инструменты (прод трогать не нужно, они ходят в биржу сами):

```bash
python3 tools/check_hyperliquid.py BTC 15            # лента сделок одной монеты
python3 tools/check_hyperliquid.py --bisect          # пошаговые подписки: на какой монете рвётся
python3 tools/check_hyperliquid.py --soak 3600       # долгая проверка канала, 1 час
python3 tools/check_hyperliquid.py --soak 1800 http://127.0.0.1:8000  # порядок любой
python3 tools/hl_find_killer.py                    # какая монета рвёт соединение
python3 tools/hl_liq_probe.py 600                   # есть ли в trades метка liquidation
python3 tools/fake_hl_server.py                     # псевдо-HL: посмотреть терминал без сети
python3 tools/hl_standalone_test.py                  # A/B: боевой корутиин в пустом процессе
bash tools/diag_hl.sh                                # сводка: REST, WS-матрица, health
```

Число в аргументах `--soak` — длительность в секундах, адрес сервера можно
указать до или после числа (по умолчанию `http://127.0.0.1:8000`).

`--bisect` проходит соединение за ~16 с и проверяет только темп подписок.
`--soak` держит соединение минуты/часы с тем же интервалом пинга, что у боевого
слушателя: следит, что приходит `pong` и что входящие не молчат; при обрыве
печатает код закрытия и время жизни соединения (код выхода 0 — пережил весь
срок, 4 — умер; удобно вешать в cron). Если `--soak` живёт часами, а боевой
слушатель рвётся — причина в боевом коде/окружении сервера; если умирает и
этот зонд — это биржа/сеть.

`tools/hl_find_killer.py` отвечает на вопрос «какая именно монета рвёт
соединение». Он проходит ровно боевой список монет (тот же `universe` и тот же
`hl_coin_map`) по одной, читая каждый кадр, и печатает виновника; найденные
монеты исключаются, проход повторяется до чистого прогона. В конце скрипт
выдаёт готовую строку для systemd:

```
--- проход 1: 23 монет
    [  0.3с] kPEPE: ОШИБКА подписки {"error": "no such coin: kPEPE"}
    [  0.3с] УМЕР: CLOSED close_code=1000; последняя монета=kPEPE
  >> виновник прохода 1: kPEPE
--- проход 2 (исключено: ['kPEPE']): ЖИВ
```

`tools/hl_liq_probe.py` отвечает на вопрос «а отдаёт ли HL ликвидации вообще».
Соединение может быть идеально живым при `events: 0`, и причины две: ликвидаций
просто не было, либо биржа не помечает их в публичном канале `trades`
(в документации HL тип `WsTrade` — это `coin/side/px/sz/hash/time/tid/users`,
без поля `liquidation`; оно описано только для `WsFill` из приватного
`userFills`). Зонд считает сделки и сделки с объектом `liquidation`, печатает
фактические наборы полей и пример — по ним видно, какой это случай.

`tools/fake_hl_server.py` поднимает локальную псевдо-биржу (universe + trades
с ликвидациями + pong), чтобы смотреть терминал без доступа к биржам:

```bash
python3 tools/fake_hl_server.py 8899 2.0 &
LIQSCOPE_HL_WS=http://127.0.0.1:8899/ws LIQSCOPE_HL_REST=http://127.0.0.1:8899 \
LIQSCOPE_DEMO=1 python3 -m uvicorn server:app --host 0.0.0.0 --port 8000
```

`tools/hl_standalone_test.py` запускает **боевой корутиин** в пустом процессе
и сравнивает три конфигурации: отдельная сессия (текущий дефолт), общая боевая
сессия (`LIQSCOPE_HL_SHARED=1`) и голый клиент-контроль. Он отвечает на вопрос,
кто именно рвёт соединение — сам код, общая сессия или сеть:

```
ВАРИАНТ 1 жив, ВАРИАНТ 2 умер  → держим дефолт (отдельная сессия)
ВАРИАНТ 1 умер, ВАРИАНТ 3 жив  → баг в market_feed (в выводе — код закрытия)
ВАРИАНТ 3 умер                 → биржа/сеть режет всех с этого IP
```

## Если данных всё равно нет

1. `curl -s localhost:8000/api/health` — смотрим `sources`.
2. `connected: false` + `last_error: Cannot connect …` — сервер не пускают
   к бирже (файрвол/страна). Проверить руками:
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' https://fapi.binance.com/fapi/v1/ping
   curl -s -o /dev/null -w '%{http_code}\n' https://api.bybit.com/v5/market/time
   ```
   Лишние биржи можно отключить: `LIQSCOPE_EXCHANGES=bybit,okx`.
3. Нет тиков (`ticks_seen: 0`): смотрите `tick_source`, `hot_symbols` и
   `tick_subscriptions` в `/api/health`, плюс `journalctl -u liqscope | grep ticks`.
   Если источник «молчит», через 20 с движок сам уйдёт на следующий
   (combined → raw → Bybit) и напишет об этом в лог.
4. Binance принимает подписку (`{"result":null,"id":1}`), но сделок не шлёт —
   такое бывает на отдельных серверах. Терминал сам уйдёт на Bybit; чтобы не
   ждать 40 с после каждого рестарта, поставьте `LIQSCOPE_TICK_SOURCE=bybit`.
   Подтвердить руками: `python3 tools/check_exchanges.py`.
5. `connected: true`, но `events: 0` — рынок спокойный: ликвидации по
   топ-монетам идут каждые несколько секунд, но в штиль могут быть паузы.
   Проверить можно, выставив «Мин. объём = Все» и монету «🌐 ВСЕ».
